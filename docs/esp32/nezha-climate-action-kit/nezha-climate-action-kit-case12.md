# 案例十二：城市气候安全站

## 案例简介

当城市同时面临高温、强光与积水时，一个模型如何协同响应？城市气候安全站整合温湿度、水位、光照、气压、姿态与 RFID 互动，在 **Nezha ESP32** 的协调下完成显示、风扇降温、遮阳与积水警戒，并可将数据上传至 SmartIoT。学生综合运用前面案例的知识，设计一套可解释、可测试的系统。

学生将通过搭建、编程和测试，把观测结果与模型的显示或动作联系起来，学习用数据解释现象。

通过本案例，学生可以结合课堂观察与工程实践，思考如何利用技术改善校园和城市环境。

## 教学目标

完成本案例后，学生能够：

1. 梳理多个输入、判断规则和执行输出之间的对应关系。
2. 为共享执行器设计优先级，避免命令冲突。
3. 使用状态与计时方法协调多个任务。
4. 制定组合测试计划，并用记录解释系统表现。
5. 根据测试结果调整参数，经历“设计—编程—测试—改进”的工程实践过程。

## 课程引入

请各小组扮演城市设施设计团队：同一站点可能出现高温、强光、积水和刷卡请求。列出系统需要完成的任务，讨论哪些任务应优先，再将方案画成输入—规则—输出表。

本节课中，我们将扮演“城市环境设计师”，搭建城市气候安全站，用实际观测检验自己的设计。

## 学习探究

在开始搭建前，可以分组讨论以下问题：

1. 积水警戒与刷卡开闸同时发生，谁优先？
2. 一个动作等待几秒时，其他传感器还能及时更新吗？
3. 所有模块能否同时连接并由当前电源稳定供电？
4. 你会怎样记录测试条件，说明结果是否符合预期？
5. 如果把模型应用到真实环境，还需要考虑哪些因素？

## 搭建步骤

按照搭建说明完成城市气候安全站的底座、主控安装位和相关功能结构。

搭建时重点检查：

- 先分区搭建感知区、遮阳区、通行/警戒区，保证机构互不碰撞。
- 将水位实验容器与电源、主控及接线区域隔离。
- 制作实际端口分配表，逐项检查供电需求和总线地址。
- 分别验证每个子模块，再逐个加入总模型；保留统一停止手段。

## 程序设计

程序分为“启动初始化”和“循环运行”两个部分。

### 1. 启动初始化

<!-- 图片占位符：启动初始化程序截图 -->
<!-- 建议文件名：./images/urban-climate-safety-station-program-init.png -->

程序启动后将执行以下操作：

1. 列出每个子任务的输入、阈值、状态、输出与更新周期。
2. 初始化屏幕与数据变量，避免沿用上一次运行的状态。
3. 在屏幕预定位置显示数据标签与初始运行状态。

主控盒屏幕的显示布局如下：

| 屏幕行 | 显示内容 |
| ---: | --- |
| 第 1 行 | 系统状态 |
| 第 2 行 | 各传感器读数与有效性 |
| 第 3 行 | 运行状态 |
| 第 4 行 | 警戒 / 通行 / 执行器状态 |

### 2. 循环检测与控制

<!-- 图片占位符：循环检测与控制程序截图 -->
<!-- 建议文件名：./images/urban-climate-safety-station-program-main.png -->

在 `forever` 循环中，系统会持续执行以下任务。

#### 状态设计

- 建议分别记录风扇、遮阳、积水、姿态和刷卡状态，不让多个任务直接争抢同一执行器。

#### 优先级

- 若警戒与刷卡共用闸门，建议警戒优先、暂停通行；若独立机构，明确各自含义与动作范围。

#### 循环协调

- 用计时更新采样、动作和上传任务；避免长时间等待阻塞其他判断。

#### 异常处理

- 为读数失败、网络离线和设备重启设计可解释的提示与安全输出。

### 3. 关键参数

| 参数 | 示例值 | 含义 | 调整建议 |
| --- | ---: | --- | --- |
| 温度、光照、水位、姿态阈值 | 待实机确认 | 机械和安装变化后再次校准 | 继承已验证子案例并重新实测 |
| 执行器优先级 | 待实机确认 | 按最终模型和程序明确规则 | 警戒优先于普通互动（建议方案） |
| 采样、动作与上传周期 | 待实机确认 | 遵守模块及平台支持范围 | 分别设置 |
| 电机目标和供电配置 | 待实机确认 | 未验证前不填写固定接口与角度 | 按实际整机确认 |

:::note
系统先采集数据，再按各子任务更新状态，最后统一输出。温度用于风扇控制、光照用于遮阳、水位与姿态用于警戒、RFID 用于互动计数，气压用于趋势记录。完整整合须先核对接口数量、总线地址、库支持及电源能力；若资源不足，应分阶段搭建或拆为协作站点，不能默认全部硬件可同时接入。
:::

:::caution
先核对接口资源、总线地址与供电能力，再逐步加入模块。水位实验区与主控和电源隔离，并检查共享执行器的优先级。
:::

## 运行测试

完成程序后，按以下顺序测试：

1. **启动检查**：连接设备并下载已验证程序，确认初始化状态与屏幕标签正确。
2. **逐个触发温度、光照与刷卡条件**：每个子系统独立运行，状态与动作一致。
3. **同时模拟强光与高温**：遮阳与风扇均能响应，屏幕持续更新。
4. **警戒时再刷卡**：共享执行器按约定优先级工作，不被普通事件覆盖。
5. **上传时改变环境并临时断网**：本地判断仍运行，平台恢复后继续接收新数据。
6. **重启模型**：计数与状态符合约定，机构无意外持续动作。
7. **复测与记录**：改变一个条件后重复测试，记录输入、输出与结果；结束时停止执行器。

如果出现“加模块后运行不稳定”，逐项检查总线地址、库兼容、接口分配和电源负载，分批复测。

如果出现“动作期间无法及时报警”，减少长时间阻塞等待，用状态与计时拆分动作。

如果出现“同一电机来回动作”，检查是否由多个子任务同时控制，统一输出并设置优先级。

## 扩展挑战

### 挑战一：记录状态变化时间

记录警戒、风扇、遮阳与通行状态改变的时间。根据日志解释系统对输入变化的响应顺序。

### 挑战二：设计组合测试清单

列出单一条件、同时触发、恢复和异常场景。为每项写明预期输出，再逐项验证。

### 挑战三：增加异常恢复机制

为读数失败、断网和重启分别设计处理方式。测试恢复后是否重新读取有效数据并返回正确状态。

### 挑战四：优化任务更新周期

分别调整采样、显示和上传周期。比较响应速度，检查某个任务是否阻塞其他任务。

### 挑战五：开展小组交叉验收

交换小组作品与测试清单，按照同一标准检查。记录功能、接口与供电方面的限制，并给出改进建议。

## 扩展知识

### 为什么需要任务优先级？

多个任务可能同时要求控制同一机构。先明确优先级，再统一输出，可以避免刷卡动作覆盖警戒动作，或同一电机反复收到相反命令。

### 什么是状态与计时？

状态记录系统当前正在做什么，计时决定何时进行下一步。把长动作拆成状态变化，可以减少等待对其他采样和提醒任务的影响。

### 系统整合为什么需要逐步测试？

模块数量增加后，可能出现接口不足、总线地址冲突、供电不稳和程序阻塞。先单模块测试，再逐步组合，有助于定位问题。
